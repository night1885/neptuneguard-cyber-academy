# Write a reproducible report without inflating impact

## Goal and boundary

Turn a supported observation into a clear, minimal report. Use only findings collected under current program permission. A practice draft about this course's synthetic examples must never be submitted to a real program as a discovered company vulnerability.

A useful report connects the actor, asset, preconditions, steps, result and violated rule. Severity follows supported consequence and program policy, not a tool label or desired payout. A duplicate or no-finding outcome does not justify exaggeration or extra unauthorized testing.

## Build the report privately

Use a local Markdown editor in an approved private workspace. No reporting API, account credentials or automated submission is needed. Work through these fields:

1. Title: name the boundary and supported consequence, not just critical bug.
2. Target: select the actual permitted affected asset. An Other field is not a way around scope.
3. Preconditions: account roles, ownership/sharing, relevant state and environment. Do not include passwords or live tokens.
4. Steps: exact minimal order, including identity verification and the positive control. Use permitted controlled records; do not add enumeration to show scale.
5. Expected behavior: cite the applicable documented/business rule.
6. Actual result: relevant fields and status, with reviewed evidence references.
7. Demonstrated impact: state what the evidence establishes and separately identify assumptions.
8. Final state: cleanup actually performed, remaining test artifacts and uncertainty.

## Worked synthetic report

Title: Controlled nonowner can read a private synthetic draft.

Preconditions: A owns fictional record demo-1; B is an independently verified controlled account; the hypothetical rule limits reads to the owner.

Steps: verify A, read demo-1 successfully; verify B, request that same synthetic object with B's coherent authentication context; inspect only its synthetic title. Actual: B receives Synthetic draft. Expected: B denied under the stated rule.

Supported impact: one controlled cross-owner read. Not demonstrated: writes, deletion, anonymous exposure, access to all tenants or account takeover. This is fictional training evidence, not a live company finding.

## Platform workflow

Read the current brief and official submission guidance. On Bugcrowd the report flow includes title, target, technical severity, vulnerability details and supporting evidence. Review disclosure terms and the complete draft before submitting a genuine report. Interface fields and limits can change; use the live official form rather than stale screenshots.

Review screenshots/videos for headers, cookies, address bars, notifications, unrelated users and private-program details. Do not add collaborators or share evidence outside the program's permitted routes without applicable permission. Submission, clarification, retesting, award and payout are separate stages.

## Exercise and explained answer

Rewrite 'all users fully compromised' using only the synthetic evidence above. A suitable answer is 'B could read A's controlled private draft; broader access and modification were not tested.' It is more useful because another reviewer can trace each claim to a specific observation.

What if triage cannot reproduce? Confirm mode, account ownership, current sessions, exact order and state. Answer the actual question; do not perform destructive escalation or public disclosure to force attention.

## Troubleshooting and cleanup

If evidence is inconclusive, retain a private research note rather than submitting an invented finding. Do not submit a template solely to finish the lesson. Keep only allowed minimal artifacts and follow the applicable retention/disclosure rules; no payout is required for learning completion.
