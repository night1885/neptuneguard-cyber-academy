# Two-course private workspace integration candidate

This is a coordinated source implementation for student-package representation, two-course private reading navigation and Save/Resume integration. It is not a completed course or a live release. The controller is default-off and no existing startup, router, registry, authorizer, workflow, bookmark schema or Community Learning file is changed. The new workflow is additive. No Discord API call or production database operation occurs by importing these modules.

## Components and composition
formal-student-packages.mjs validates explicit student-package data, copies/freezes it, bounds page text/aggregate size and computes a SHA-256 publication revision from the content/review reference. It accepts only the two intended formal course keys. A package must contain courseKey, title, audience='student', reviewRef and lessons with unique key/title/pages. Each page is complete pre-reviewed text of at most 1,200 JavaScript characters; the factory rejects oversize pages instead of truncating teaching. Total bounds are 200 lessons per course, 10,000 pages and 4 MiB page bytes across the set. It performs no filesystem, URL, document-link or fixture import.

The in-process package identity marker prevents passing a copied arbitrary loader interface. It does not prove that a review reference is genuine, detect every leaked answer, authenticate an author or make an owner book safe to publish. A human must actually prepare/review the full student corpus and instructor separation. No real student packages are authored or approved by this batch; test content is visibly synthetic.

Build the bookmark service from packageSet.bookmarkMetadata() and the existing transaction-bound bookmark authorization adapter, using a separately reviewed restricted PostgreSQL pool/schema profile. Build createFormalCourseWorkspace with that same packageSet, bookmarks service and current authorizeCourse provider. The latter returns actorId/courseKey/studentId, as the existing formal course authorizer does. Do not substitute client-supplied enrollment/member Booleans or course claims.

The controller requires explicit guild, entry channel, bot user, entry message and verified-role IDs, plus readiness/clock providers. It verifies the configured bot-authored entry panel. Known entry IDs are fws:open:ethical-hacking and fws:open:incident-response; it creates opaque single-use per-view action IDs only after a valid entry. This document does not publish an entry panel or authorize any real IDs/configuration.

## Interaction and persistence behavior
Opening acknowledges privately. Normal navigation edits the same private message, with no learner slash command or modal. Overview, Start, Next, Back, Help, Reading status, Save position and Resume are implemented over all supplied lessons/pages for either course. Guild/member role and authoritative course/student binding are checked before provider access and again before rendering. Actor/course/message/author/private-flag/origin checks prevent using another learner's controls. Mention parsing is disabled; text and controls remain bounded.

Session slots are reserved before asynchronous opening; per-actor/course in-flight limits, provider capacity/timeouts, monotonic clock checks, expiry and single-use controls limit replay and stale actions. A stale or foreign control receives a neutral private denial rather than editing the owner's workspace. Re-entry creates fresh controls. Normal reading does not automatically save.

Save uses the existing bookmark service's expected version and current publication. A conflict triggers a read/review message, never an automatic write retry. Resume reloads the authoritative saved position; unknown/revised positions cannot silently route to an old page. Reading location, Help and status do not award completion, permission, grades, XP, badges or certificates. Enrollment/account admission and submission/reviewer decisions are not implemented by this reader.

Provider timeout, context loss or revocation neutralizes the affected view. A persistence timeout or revocation after a database write may leave a committed position; suppressing display is not undoing that write. The controller does not promise distributed instantaneous revocation or cancel an already issued database/Discord request. Bounded disposal waits for tracked provider and handler promises, returning drained=false if the deadline expires. Integration must respect that result. Private SDK acknowledgment checks are necessary, not a substitute for live Discord acceptance and configuration review.
