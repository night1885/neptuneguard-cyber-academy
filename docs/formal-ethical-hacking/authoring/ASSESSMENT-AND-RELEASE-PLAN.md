# Assessment and release plan — proposed gates

Draft design supporting [the programme blueprint](../PROGRAMME-BLUEPRINT.md), not an implemented grade, enrolment rule, lab permission, award or deployment approval. It complements the existing [pilot](FIRST-JOURNEY-PILOT.md), [workflow contract](FIRST-JOURNEY-WORKFLOW-CONTRACT.md) and [integration inspection](WORKFLOW-INTEGRATION-REVIEW.md). Their unresolved decisions are not resolved merely by this plan.

## Evidence of understanding
Assess observable reasoning, scope adherence, technical execution, reproducibility, impact interpretation, repair/retest and communication. A tool output or proof string alone is insufficient. Proposed coaching descriptions are not-observed, demonstrated-with-guidance, independent-on-familiar-task and independent-on-unfamiliar-task. They are not runtime states or calibrated pass bands. Do not convert them into a numeric pass mark without independent assessor work.

Reduce hints as students progress. Record interventions separately from independent performance. Provide accessible text alternatives and test keyboard usability. Use fresh, original task variants and authentic explanations rather than memorized transcripts. Any safety/privacy breach needs the actual incident process; it must not be hidden by an aggregate score.

## Proposed integrated assessment milestones
- Foundation investigation: supported setup, system/network explanation, bounded observation, controlled recovery and minimal evidence report.
- Professional assessment: an explicitly scoped synthetic engagement requiring planning, enumeration/validation, permitted impact demonstration, findings, remediation and retest. Include legitimate behavior and false-positive controls.
- Advanced web investigation: an unfamiliar owned teaching application with source analysis, a reasoned vulnerability hypothesis, controlled custom proof, reliable reproduction, repair/regression and a professional explanation.
- Stakeholder handover: technical report, concise management summary, priority justification, uncertainty, remediation discussion and verified retest status.

These are assessment designs to author and validate, not executable lab briefs, exact vendor exam simulations or additional requirements silently attached to existing capstones. Existing capstones retain their stated scope.

## Separate decisions
A student may demonstrate a specific professional task without holding every target credential. Conversely, passing an external exam does not automatically establish all proposed job-role outcomes. Keep target-specific exam readiness, role-task competence, academy completion, enrolment, course assignment, restricted-lab permission and awards separate. No employment, accreditation or certification result is guaranteed.

## Release gates
| Gate | Required evidence before the associated claim |
|---|---|
| Design baseline | Reviewed graduate outcomes, role profile, current provider reconciliation, complete prerequisite and assessment design |
| Curriculum validation | Semantic review; practical starter/repair checks; independent-task variants; original reports; calibrated reviewer decisions |
| Lab operations | Supported OS/architecture routes, approved media/tools/transfer/licensing, isolation/recovery reproduction, support and incident procedures |
| Private workflow | Approved Discord/web decision; current actor/course/reviewer authorization; bounded evidence; retention/deletion; tested revision, concurrency and dependency-failure handling |
| Internal rehearsal | Complete private learner/reviewer journey and lab route reproduced with synthetic data, interventions and retests recorded |
| Learner pilot | Approved participant/privacy/support arrangements, accessibility review, resolved mandatory blockers and explicit limited scope |
| Production activation | Current full-checkout checks, reviewed integration/security tests, staging demonstration, configuration/secret review, backup/restore and rollback rehearsal, then separate deployment and activation approval |

The final activation items are proposed acceptance work, not assertions about a live service or its current configuration. No migrations, Render settings, database connections, Discord handlers or feature flags are changed by this batch. Community Learning is excluded.

Work in coherent packages with one evidence-backed review per package. Do not repeatedly expand optional worksheets while leaving core curriculum gaps and delivery blockers untouched. Record actual measured effort when available; no unsupported completion percentage or delivery date is assigned.
