# First-journey pilot — maintainer execution plan

Draft plan, not an executed pilot or release approval. It accompanies [Start here](../START-HERE.md), the [worksheet](../FIRST-PRACTICAL-WORKSHEET.md) and the existing EH-LAB-00 through EH-LAB-05 sequence with Linux foundations. No learner runtime, private submission service, hosted lab or assessment automation is implemented.

## Gate A — allow an internal rehearsal only when ready
Before any practical rehearsal, record the exact branch/commit, reviewed exercise scope, responsible reviewer, supported host/guest/hypervisor candidate and permission to install. Confirm approved incident escalation, dependency provisioning, material transfer, private evidence handling and retention/deletion arrangements. If a required route or policy is absent, record BLOCKED and restrict work to document review; do not recruit a real learner to discover an unsafe operational gap.

Use clean student-owned guest candidates, not production or managed organizational systems without approval. Establish platform-specific resource and architecture support by reproduction; do not convert one successful machine into a universal minimum. Any configuration outside the tested route needs a separate result.

## Gate B — reproduce the complete route
Follow the linked lessons in their stated scope rather than silently repairing instructions. Capture the action, observed result and intervention at each stage:

1. Authorization/readiness: can the participant identify exact scope, exclusions, stop conditions and support?
2. Media/installation: can the candidate route authenticate media and install without an unexpected download or external adapter?
3. Tools and transfer: are required tools and reviewed offline materials available without ad hoc NAT, bridging or unsafe sharing?
4. Terminal foundations: can the participant distinguish host/guest, directory, permissions, error output and exit status?
5. Two-VM configuration: are guest identities distinct, all adapters/integrations reviewed, and relevant IPv4/IPv6 routes explained?
6. Recovery: do the scoped connectivity, controlled network-name fault and narrow snapshot test produce explainable actual observations? Is configuration rechecked after rollback?
7. HTTP observation: does the intended clean directory serve only the fixture, bind to the specific peer address, and support the permitted GET/HEAD observations?
8. Shutdown: are server stop, listener recheck, the permitted stopped-service observation and guest final state recorded?
9. Reporting: can the participant correlate evidence, explain uncertainty and prepare minimal redacted records without publishing personal information?
10. Feedback: can a reviewer provide a specific correction or bounded repeat without treating the draft dimensions as a calibrated pass mark?

Do not execute later scanning or security-repair exercises as part of this pilot. Do not use public targets to demonstrate isolation. A blank or blocked checkpoint is not a pass.

## Record problems so they can be fixed
Use issue references or a private approved record appropriate to the information. Do not place learner identities, submissions, secrets or personal screenshots in public issues. Suggested non-sensitive record fields:

| Field | Record |
|---|---|
| Checkpoint and lesson section | To complete |
| Exact commit and candidate versions | To complete |
| Expected instruction, not presumed success | To complete |
| Actual observation and evidence reference | To complete |
| Participant interpretation | To complete |
| Reviewer intervention, if any | To complete |
| Classification: instruction, compatibility, provisioning, safety, accessibility or policy | To complete |
| Owner and proposed bounded fix | To complete |
| Retest configuration and result | Not executed until recorded |

Record task durations only when actually measured. Distinguish a reading ambiguity from a software defect or unsupported configuration. An instructor rescue is an intervention, not proof of independent completion.

## Gate C — review and repeat
An internal rehearsal supports only its recorded configuration and scope. Reproduce fixes from a clean documented baseline; test the relevant recovery and stop conditions again. Review keyboard-only access, readable commands, clear guest-role labels and equivalent text evidence rather than requiring decorative screenshots. Document accommodations without collecting medical information.

Before an approved beginner pilot, resolve mandatory setup, privacy, support and authorization gaps and establish the real participant process. Before publication, additionally complete hardware reproduction, semantic content review, calibrated assessment and accessibility review plus the existing release blockers. A local checklist, one successful rehearsal or passing metadata tests cannot activate the course. Deployment and activation remain separate approvals.
