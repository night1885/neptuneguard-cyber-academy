# Combined private confirmation navigation correction

This batch changes only the existing learner/reviewer acknowledgement paths. It creates no learner field, student identifier, grant scheme, database table, command or published entry. The existing permanent student ID, work/report identities, source digest checks, authorization providers, operation keys and expiry policies are unchanged.

Learner start/confirm/cancel buttons now use deferUpdate when supported. Preview modals use it only when isFromMessage returns literal true. Reviewer confirm/cancel buttons and message-origin feedback forms receive the same behavior; existing report/feedback navigation already supported in-place updates. Choose controls still open their existing modals directly, without a second acknowledgement.

All these paths retain the configured guild/application/channel and bot-authored ephemeral-origin checks before acknowledgement, plus existing guards before protected output. An explicit non-message-origin modal is rejected before provider work. Adapters without update support retain the existing explicit flags:64 reply fallback. This is compatibility behavior, not a claim that fallback adapters update in place. No acknowledgement fallback is attempted after a failed native update, and delivery failures retain only the original same-key confirmation control rather than repeat a mutation automatically.

The regression suite covers every changed learner/reviewer phase, SDK payload serialization, direct modal opening, compatibility reply paths, non-message/public/wrong-guild rejection, receipt delivery failure, readiness loss and disposal during pending work. It is included by the existing certification test glob. Existing PostgreSQL acceptance remains required at the committed head, including its composition and real-reader journey. No local execution or future CI pass is claimed here.

This correction reduces additional private replies on supported paths; it is not timed erasure of earlier replies, durable consent or restart-safe confirmation recovery. It does not publish controls or change startup wiring. Production readiness, privacy/resource verification, durable recovery, provisioning, cleanup/reconciliation and native Discord acceptance remain separate release requirements. No live listener, collection, migration, grant, permission change, merge or deployment is performed by this batch.
