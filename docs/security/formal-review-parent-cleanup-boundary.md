# Conservative legacy shared-enrollment cleanup boundary

The staged shared-enrollment retention executor's foreign-key inventory does not capture review work's logical student reference: migration 012 deliberately has no enrollment foreign key. Until a complete scoped review cleanup/reconciliation contract exists, observing the formal_review namespace now makes its legacy four-table catalog profile inadmissible. The executor rolls back before preservation review or deletion. This blocks the database broadly, including unrelated subjects, empty namespaces and review tables the executor cannot read; it does not infer clearance from missing SELECT privileges or zero visible rows.

Both existing course and parent DELETE predicates also require namespace absence. Their existing row-count checks roll back if a newly observed namespace suppresses a deletion. These checks are conservative refusal, not a review-data executor, scoped purge receipt, migration grant or proof that all logical dependencies are inventoried. Snapshot hashes, student IDs, retention/preservation rules, default-off configuration and legacy permissions are unchanged. Closed-application and audit-retention executors are not modified by this batch.

The checks do not make independent review schema introduction or provisioning atomic with cleanup. Concurrent schema changes must remain excluded by deployment controls; no claim is made that catalog checks eliminate every DDL/provisioning race. In a database with formal_review installed this legacy executor must remain blocked until separately reviewed integration is implemented. It must never be enabled merely to test the refusal against live data.

The new unit regression checks early refusal, rollback and no DELETE. Disposable PostgreSQL 16/18 acceptance creates a unique fixture database, a service-approved fictional student with the existing student ID, and a restricted legacy executor role. It tests empty and populated unreadable review namespaces, unchanged enrollment/course/lab/audit/work data, no preservation request and no DELETE statements. Existing shared-retention suites remain responsible for legacy-schema positive/rollback coverage. Source addition is not a local execution or future-head CI pass.

No real record is deleted, no cleanup scheduler or live route is added, and no production role, privilege, migration, configuration, publication, merge or deployment is changed. This is a partial safety boundary, not completion of course-content retention or Discord erasure.
