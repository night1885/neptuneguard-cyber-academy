# Independent audit expiry - staged backend

Default-disabled library only; no runtime/CLI/scheduler, production credentials, grants or activation are supplied. A separate restricted direct login, explicit database/schema and owner, and a trusted preservation-review provider are mandatory. The application login is rejected. Audit UPDATE/INSERT/TRUNCATE/TRIGGER and mutation privileges on enrollment/course/lab tables are rejected; fixture grants use SELECT(event_id,created_at) plus audit DELETE only.

The executor reads only event_id as exact text and the UTC created_at timestamp with six fractional digits. It does not read actor/subject IDs, action or private details. It reuses the existing microsecond-aware classifier and rechecks the three-calendar-month UTC boundary in the guarded DELETE with PostgreSQL calendar arithmetic. Month-end clamping is not an inverse subtraction or a 90-day approximation. The default host-clock cutoff pads milliseconds with zeros, conservatively waiting until the next representable millisecond when necessary; the trusted test-clock injection is not an end-user parameter.

One event is considered per invocation. A conservative table lock serializes competing writes without granting audit UPDATE for row locks. Unknown inbound foreign keys, user delete triggers and rewrite rules block deletion. Parent enrollment/course/lab records are not touched. Review decisions bind actor, event ID, exact timestamp and category, have bounded validity and a bounded callback wait; no approved production preservation workflow or durable review register is implemented. Fixture allow providers must not be used as production defaults.

A search path pinned to pg_catalog protects built-in resolution; table names are separately qualified. Statement/lock/idle timeouts and a query-admission budget are not a universal operation-cancellation guarantee. Callback abort is cooperative; pool bounds and production workload/clock review remain the caller/operator's responsibility. COMMIT acknowledgment errors remain potentially ambiguous; no blind retry or erasure guarantee is supplied.

Local mocked tests passed using transcribed equivalents of existing classifier/calendar algorithms, not a full local repository checkout. Real PostgreSQL acceptance cases are syntax-checked, not locally executed. The proposed CI step will exercise actual repository imports on disposable PostgreSQL 16/18, with isolated schemas/roles and a non-UTC session, exact large IDs, microsecond/month-end boundaries, independent record preservation, concurrency, blocked dependencies/permissions/review and pre-commit rollback. Passing CI is not production acceptance, provider-copy erasure, preservation-process approval or activation permission.

Shared enrollment completion deletion, scheduling/retries/alerts, operational preservation/evidence retention, providers/logs/backups, final documents, live configuration and target acceptance remain separate release gates.
