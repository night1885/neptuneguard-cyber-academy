# Shared completed-enrollment snapshot - evidence binding only

This pure helper prepares an exact, deterministic completion-set fingerprint for a future restricted deletion transaction. It has no database pool, query, deletion, review provider, scheduler or runtime entry. executionAuthorized is always false. It does not replace the existing preview or establish production readiness.

The caller must supply current target database/schema, subject, enrollment/course metadata, explicit zero lab count and empty unreviewed-dependency result after a separately reviewed locked catalog/data inspection. The helper cannot verify those supplied facts, permissions or target binding itself. Do not accept them from untrusted client input as deletion authority.

It requires prior approved enrollment metadata, a permanent ID, approved/suspended/revoked status, no closure metadata, and a nonempty unique course set with recorded administrative completion for every course. It does not require reinstatement to represent completed suspended/revoked records. Course timestamps must be canonical UTC with six fractional digits and exact millisecond evidence; approval microseconds remain exact in the fingerprint. Future, inconsistent, partial or oversized evidence fails closed. The 50-course bound is a proposed bounded-operation limit, not a retention period; larger sets require review.

The SHA-256 binds target database/schema, account/status/permanent ID/approval metadata and the sorted exact course set, timestamps and assigning/completing actors. It is deterministic evidence binding, not a signature, legal clearance or proof of source authenticity. The output and course-key list are frozen without mutating inputs. A later as-of timestamp does not change unchanged eligible record evidence. No delay beyond the recorded final completion is invented.

A future executor must lock and reread state, validate actual dependency/privilege shapes, bind a fresh preservation decision to this snapshot, remove only the reviewed completed course children before the parent in one transaction, and preserve audit/lab records. Lock order must account for the existing parent-first assignment/completion services and uncoordinated child writers; timeout/deadlock rollback and race acceptance remain mandatory. No shared-record deletion transaction is supplied in this batch.

Local tests run against the actual helper using only Node built-ins; no service or deadline stub is used. Existing certification unit globs discover the tests, and the early syntax check includes both new files. No database, provider, production configuration, learner data, merge or deployment changes occur. Preservation workflow, shared deletion, scheduling/retries/alerts, final documents and target acceptance remain release gates.
