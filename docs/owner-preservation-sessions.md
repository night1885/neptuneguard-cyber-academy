# Owner-only shared-enrollment review intent sessions

This staged, default-disabled library prepares a two-step owner confirmation protocol for completed shared enrollments only. It has no Discord/runtime binding, database connection, persistence, clearance writer, executor invocation, scheduler, environment activation or production credentials. Closed-application and audit-event confirmation sessions are not implemented by this batch.

Only the configured owner in the configured server may begin, confirm or cancel. Administrator permissions and named roles do not grant authority. The future handler must derive actor/server identity from an authenticated interaction; comparing supplied ID strings here is not authentication. Never pass client-asserted identities as authenticated context.

A trusted readCompletionState implementation must return a consistent server-side read of enrollment/course metadata and dependency information, plus explicit preservationRequired=false and uncertain=false. Missing or unresolved preservation status blocks progress; do not invent false defaults. The existing snapshot helper revalidates completion/dependency eligibility and binds the configured database/schema/subject. Reader-supplied scope and clocks cannot override factory configuration.

Begin reserves bounded process-local capacity before awaiting the read, then returns an opaque random UUID token and minimal evidence for a future private owner review screen. No raw enrollment record or permanent student ID is returned by this library. The five-minute maximum token lifetime starts before reading. A confirmation requires the explicit reviewed-no-preservation-required attestation, consumes the token before any asynchronous work, and re-reads current evidence. Changed snapshots, new active courses, linked labs, unknown dependencies, uncertainty or preservation requirements reject confirmation. Failed or canceled confirmation requires a new review; concurrent confirmation can yield at most one intent per token in this process.

The result is an owner_review_intent with clearanceIssued=false and executionAuthorized=false, NOT a trusted stored clearance or deletion authorization. It deliberately omits the decision=allow and completed-review fields required by the clearance reader. Future authenticated issuance/storage must independently validate preservation obligations and coordinate revocation/consumption with execution; this session does not close that concurrency gap. A required preservation obligation cannot be waived by an owner attestation.

Pending entries are temporary process memory, disappear on restart, and are pruned on later begin calls; the fixed maximum bounds stale entries even without background cleanup. They are not a durable legal-hold register or audit trail. Expiry/cancel removes pending state but does not prove erasure of process/provider copies. Read timeouts signal cooperative cancellation, not guaranteed cancellation of database work.

Local tests run the actual new module with the unchanged snapshot helper reconstructed from the verified Git blob 00e10eb9a56ad4e1d31c6f03495477eb217ffa8e. Readers are fixtures: authenticated Discord delivery, actual SQL consistency, durable storage, multi-process serialization, operational review and production acceptance remain unverified. No production record query, deletion, grant, migration, published control, merge or deployment is part of this batch.
